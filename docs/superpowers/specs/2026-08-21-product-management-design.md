# 商品管理全栈实战设计规格

## 1. 背景与目标

本项目交付一个可运行的商品管理全栈 Demo，覆盖培训题目的商品发布与商品管理基础功能，并实际实现以下两个加分方向：

1. 通过版本化字段模板支持实物商品、虚拟商品和广告素材三种业务模型。
2. 为其他系统提供具备缓存保护、限流、降级和压测证据的高 QPS 商品详情接口。

技术栈为 React + TypeScript、Python 3.12 + FastAPI、PostgreSQL、Redis。全部服务通过 Docker Compose 一键启动。

## 2. 范围

### 2.1 本期包含

- 固定管理员账号登录与 JWT 鉴权。
- 商品管理：分页、组合筛选、详情、编辑、单个上下架、批量上下架，以及将单个商品设为处罚状态。
- 商品发布：公共字段、图文信息、服务与售后，以及三类商品的动态专属字段。
- 版本化字段模板、动态表单与前后端双重校验。
- 面向其他系统的高 QPS 商品详情 API。
- 自动化测试、初始化数据、k6 压测脚本和结果报告模板。

### 2.2 本期不包含

- 注册、完整 RBAC、单点登录。
- 草稿、删除、导出、操作审计。
- 订单、支付、类目、供应商、库存扣减和交易防超卖。
- 微服务拆分、Redis Cluster、数据库分片、CDC、搜索引擎与 CDN 的实际部署。

这些能力可作为容量演进方向说明，但不得在 Demo 中声称已经实现。

## 3. 总体架构

系统采用模块化单体，避免为培训 Demo 引入不必要的分布式复杂度。

- React 管理后台负责登录、商品管理和 Schema 驱动的动态发布表单。
- FastAPI 按认证、商品、字段模板、公开详情读模型四个模块组织，各模块通过明确的服务接口协作。
- PostgreSQL 是商品事实数据的唯一权威来源。
- Redis 保存公开商品详情快照，并提供空值缓存、重建锁和限流状态。
- Docker Compose 编排 Web、API、PostgreSQL 和 Redis。

管理写链路以数据库事务和一致性为先；公开详情读链路以缓存命中率、热点保护和可控降级为先。

## 4. 用户与页面

### 4.1 登录页

管理员使用环境变量配置的固定账号和密码登录。后端校验成功后签发短期 JWT；前端不保存明文密码。所有管理 API 均要求有效 JWT，公开详情 API 不要求登录。

### 4.2 商品管理页

页面支持：

- 按商品 ID 或标题关键词查询。
- 按商品类型和商品状态筛选。
- 稳定分页并显示总数。
- 查看详情和进入编辑页。
- 单个上架或下架。
- 将单个上架或下架商品设为处罚状态。
- 勾选多个商品后批量上架或下架。
- 从页面进入商品发布流程。

管理列表展示主图、商品 ID、标题、类型、价格、库存、状态、更新时间和可用操作。

### 4.3 商品发布与编辑页

公共字段遵循培训题目规则：

- 商品标题必填，最多 60 个字符。
- 商品短标题最多 120 个字符。
- 价格必填，使用非负定点金额。
- 商品详情为富文本，清理危险 HTML 后的正文最多 2000 个字符。
- 库存必填，使用非负整数。
- 主图必填且不超过 2 MB。
- 副图最多 5 张，每张不超过 2 MB。
- 发货方式为 EMS、物流或卡券。
- 退货规则为 7 天无理由或不支持退货。
- 商品状态为上架、下架或处罚。

选择商品类型后，前端读取活动字段模板并生成专属字段。编辑已有商品时不得切换商品类型，并继续使用商品绑定的模板版本，不自动升级到活动版本，避免跨模板数据迁移歧义。

三类内置模板至少包含：

- 实物商品：重量、规格、物流模板。
- 虚拟商品：有效期、核销方式、兑换说明。
- 广告素材：素材类型、投放尺寸、文件地址。

## 5. 状态模型

正常运营状态允许 `下架 → 上架` 和 `上架 → 下架`。上架或下架商品可由处罚动作变为处罚状态。处罚状态不能通过普通编辑、单个上下架或批量操作恢复；恢复处罚不在本期范围内。

批量状态更新采用全有或全无语义。只要任意商品不存在、版本冲突或不满足状态转换规则，整个事务回滚，并返回失败商品及原因。

## 6. 数据模型

### 6.1 products

商品主表包含：

- `id`：UUIDv7，应用生成；支持多实例写入并保持较好的索引局部性。
- `title`、`short_title`、`description_html`。
- `price_amount`、`stock`。
- `product_type`、`status`、`delivery_method`、`return_rule`。
- `attributes JSONB`：类型专属字段值。
- `schema_version`：发布或编辑时使用的模板版本。
- `version`：乐观锁版本号。
- `created_at`、`updated_at`。

金额不使用二进制浮点数。API 接受十进制定点值，数据库使用 `NUMERIC` 保存；序列化时返回字符串，避免 JavaScript 精度歧义。

### 6.2 product_field_schemas

字段模板表以 `(product_type, version)` 唯一标识一个不可变模板，包含 `schema JSONB`、`active` 和时间字段。同一商品类型同一时刻只能有一个活动模板。

模板发布后不可原地修改。扩展字段时创建新版本并切换活动版本；历史商品继续绑定原版本，以保证展示和校验可重复。

模板描述字段键、标签、控件类型、数据类型、必填性、长度或数值范围及枚举选项。后端将模板转换为可执行校验规则，并拒绝未知字段。

### 6.3 product_images

图片表包含 `product_id`、`kind`、`url`、`sort_order`、`size_bytes` 和 MIME 类型。每个商品恰好一张主图，副图最多五张。数据库仅保存元数据和 URL，二进制内容由 Demo 的本地静态存储承载；生产演进为对象存储与 CDN。

上传端同时验证声明 MIME、实际文件签名、大小和数量，并生成不可执行的安全文件名。

### 6.4 索引策略

- 列表使用 `(status, product_type, updated_at DESC, id DESC)` 组合索引。
- 精确商品 ID 查询使用主键索引。
- 标题关键词使用 PostgreSQL 文本搜索索引，不使用前置通配符扫描。
- JSONB 字段只有在确认参与高频筛选后才建立表达式索引，不创建无差别的全属性 GIN 索引。

浅页管理查询可使用偏移分页并返回总数；公开的大结果集接口不在本期范围。未来若管理数据量导致深分页退化，接口演进为基于 `(updated_at, id)` 的游标分页。

## 7. API 契约

所有接口使用 `/api/v1` 前缀：

- `POST /auth/login`：管理员登录。
- `GET /product-schemas/{type}/active`：读取活动字段模板。
- `POST /products`：发布商品。
- `GET /products`：后台分页与组合筛选。
- `GET /products/{id}`：管理端完整详情。
- `PUT /products/{id}`：携带 `version` 的完整编辑。
- `PATCH /products/{id}/status`：单个上架、下架或设为处罚状态。
- `POST /products/batch-status`：批量上下架。
- `GET /public/products/{id}`：公开高 QPS 商品详情。

公开详情仅返回上架商品。下架、处罚和不存在的商品统一返回 `404`，避免泄漏内部状态。

## 8. 数据流与一致性

### 8.1 发布

1. 前端获取所选商品类型的活动模板。
2. 前端按模板渲染字段并提供即时校验。
3. 请求携带商品类型和模板版本。
4. 后端读取对应不可变模板，重新校验公共字段和动态属性。
5. 商品与图片元数据在一个 PostgreSQL 事务中写入。
6. 返回创建结果；公开详情在首次请求时按需填充缓存。

如果模板已不再是活动版本，发布请求返回冲突，前端重新获取模板并提示管理员检查新增或变化的字段。

### 8.2 编辑和状态更新

请求必须携带商品 `version`。更新 SQL 同时匹配 ID 和版本号，并原子递增版本；匹配不到时返回乐观锁冲突。

数据库事务提交成功后删除 Redis 商品快照。缓存删除失败不会回滚已提交事务，而是记录指标并执行有限次数的后台重试。短暂并发窗口允许读到旧值，由 TTL 和告警控制风险。本期不引入消息队列或 CDC。

## 9. 高 QPS 公开详情

### 9.1 Cache-Aside 读取

1. API 先校验 UUID 格式并执行客户端限流。
2. 从 Redis 读取序列化商品快照。
3. 命中正常快照则直接返回，不访问 PostgreSQL。
4. 命中空值标记则返回 `404`。
5. 未命中时使用进程内 single-flight 合并本实例相同 ID 的请求，并使用 Redis `SET NX PX` 短锁保证跨实例只有一个重建者。
6. 重建者查询 PostgreSQL。不存在或非上架商品写入短 TTL 空值标记；上架商品写入带随机抖动 TTL 的快照。
7. 非重建者进行有上限的短暂等待后重试缓存；超过等待预算则受限回源或快速失败，不无限轮询。

锁使用随机令牌并通过 Lua 脚本比较令牌后释放，避免误删其他实例续建的锁。缓存值包含商品版本，便于诊断陈旧数据。

本期选择空值缓存而非布隆过滤器：UUID 格式校验已经过滤明显非法请求，空值缓存足以展示穿透保护，并避免布隆过滤器维护成本。

### 9.2 限流与降级

- 使用 Redis 滑动窗口按客户端 IP 限制公开详情请求。
- Redis 与 PostgreSQL 分别配置短连接和查询超时，故障时不无限重试。
- Redis 不可用时，API 仅允许受并发信号量限制的数据库回源，防止数据库被击穿。
- 数据库也不可用时快速返回 `503`。
- 限流返回 `429`，并附带可重试提示。

### 9.3 可观测性

应用以结构化日志和指标记录：

- 请求量、延迟 P50/P95/P99、2xx/4xx/5xx。
- 缓存命中、空值命中、未命中和重建次数。
- 数据库回源次数、重建锁竞争、限流次数。
- Redis 与 PostgreSQL 超时和错误。
- 每个响应关联 `request_id`，日志不得记录密码、JWT 或完整敏感请求体。

## 10. 错误处理

错误响应统一包含 `code`、`message`、`field_errors` 和 `request_id`。

- `400`：请求格式或字段校验失败。
- `401`：JWT 缺失、无效或过期。
- `404`：商品或模板不存在；公开详情的非上架商品也按不存在处理。
- `409`：模板版本过期、乐观锁冲突或非法状态转换。
- `413`：图片大小或总数量超限。
- `415`：文件类型不支持。
- `429`：公开读取触发限流。
- `503`：依赖故障且无法安全降级。

前端保留表单输入并把字段错误定位到具体控件；冲突错误要求刷新最新商品或模板后重新确认，不能静默覆盖。

## 11. 安全基线

- 管理员密码以强哈希形式配置，不在仓库保存真实密码。
- JWT 使用环境变量密钥签名，设置短期过期时间。
- 富文本经过服务端白名单清理，阻止脚本和危险 URL。
- 图片执行类型、签名、体积和扩展名检查。
- SQL 全部参数化；动态字段名只允许来自已发布模板。
- CORS 默认仅允许 Docker Compose 中的管理前端来源。

## 13. 压测与验收

k6 自动执行四个场景：

1. 缓存命中的热点与分散读取。
2. 随机不存在但格式有效的 ID。
3. 同一热点键同时过期。
4. Redis 故障时的受限数据库降级。

报告必须记录机器配置、容器资源、数据量、并发数、持续时间、吞吐、P95/P99、错误率、缓存命中率和数据库回源次数。

基线目标：

- 缓存命中场景相对数据库直读吞吐提升至少 5 倍。
- 正常缓存命中场景错误率低于 0.1%。
- 同一热点键失效时，观察窗口内数据库并发回源接近 1 次；若锁持有者失败，允许后继请求在锁过期后再次重建。

性能结果只对报告所列环境有效，不把本机数字表述为生产容量承诺。

## 14. UI 设计边界

UI 详细设计阶段允许委派 UI Designer 智能体，负责页面层级、组件规范、响应式布局和可访问性建议。其输出必须遵守本规格中的业务字段、操作权限、状态规则和错误语义，并由主实现流程集成和验证。

## 16. 完成标准

1. 全新环境执行文档指定的一条 Docker Compose 命令后，所有服务通过健康检查。
2. 管理员可登录并发布实物、虚拟和广告素材商品。
3. 管理页完成分页、组合筛选、详情、编辑、单个及批量上下架，以及将单个商品设为处罚状态。
4. 动态字段由不可变、版本化模板驱动，前后端均校验。
5. 非法状态转换、并发编辑、错误文件和无效请求返回明确错误。
6. 四种高 QPS 场景可重复执行并产生规定指标。
7. 自动化测试通过，README 足以让评审者独立完成演示。

## 17. 容量演进

当单机指标证明存在真实瓶颈后，再按顺序考虑应用水平扩容、Redis Cluster、PostgreSQL 只读副本、按商品 ID 分片、对象存储与 CDN、变更事件驱动的搜索或推荐读模型。每一步都必须由容量数据触发，不在本期提前实现。
