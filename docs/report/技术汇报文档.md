## 三、L1 业务扩展：版本化 Schema 驱动的多态商品

### 3.1 业务问题

实物商品、虚拟商品、广告素材共享标题、价格等公共信息，但专属字段差异明显。如果每增加一种商品就修改数据库表、前后端表单和接口模型，交付成本高且容易产生大量空列和分支逻辑。

### 3.2 核心方案：不可变、版本化的字段模板

- 公共稳定字段进入商品主模型（`title`、`price_amount`、`stock` 等强类型列）
- 类型专属字段由字段模板定义，商品仅保存对应属性值和模板版本（`attributes JSONB`）
- 前端依据模板动态生成控件，后端依据同一模板重新校验
- 模板发布后不可原地修改；新增或变更字段时创建新版本
- 历史商品固定绑定原版本，新商品使用当前活动版本
- 后端拒绝模板外未知字段，防止脏数据进入系统

### 3.3 三类内置模板

| 商品类型 | 专属字段示例 |
|----------|-------------|
| 实物商品 | 重量、规格、物流模板 |
| 虚拟商品 | 有效期、核销方式、兑换说明 |
| 广告素材 | 素材类型、投放尺寸、文件地址 |

### 3.4 为什么不用纯宽表或纯 EAV

纯宽表会随业务类型增加产生大量空列和频繁迁移；纯 EAV 模型查询、约束和开发体验复杂；完全无约束的 JSON 又容易积累脏数据。因此采用**混合模型**：稳定且高频查询的公共字段使用强类型列，变化快的专属字段存入 JSONB，并由不可变模板负责约束。

### 3.5 业务价值

- 新增商品类型或字段时，主要通过配置模板完成，减少表结构和页面硬编码变更
- 版本绑定保证历史商品可重复展示、校验和追溯
- 公共字段仍保持强类型和高查询效率，在灵活性与可治理性之间取得平衡

## 四、L3 高并发稳定：读链路防护体系

### 4.1 场景目标

其他系统可能集中读取热点商品，也可能请求大量不存在的商品 ID。系统需要避免缓存失效导致数据库瞬时过载，并在 Redis 或 PostgreSQL 故障时保持可控行为。

### 4.2 分层防护设计

| 风险 | 设计与实现 |
|------|-----------|
| 缓存穿透 | UUID 格式校验 + 短 TTL 空值缓存 |
| 热点 Key 击穿 | 进程内 single-flight + Redis `SET NX PX` 跨实例短锁 |
| 缓存雪崩 | 基础 TTL 加随机抖动，避免集中失效 |
| 锁误释放 | 随机令牌 + Lua 比较令牌后释放 |
| Redis 故障 | 受并发信号量保护的有限数据库回源 |
| PostgreSQL 故障 | 短超时、不无限重试、快速返回 `503` |
| 流量过载 | Redis 滑动窗口按客户端 IP 限流，返回 `429` |

### 4.3 请求流向

```
Client Request
  → UUID 格式校验
    → 客户端 IP 限流 (Redis 滑动窗口)
      → 读 Redis 缓存
        → 命中? 直接返回
        → 空值? 404
        → 未命中? Single-Flight + Redis 分布式锁
          → 抢到锁? 查 PostgreSQL → 写缓存 → 返回
          → 未抢到? 等待缓存重建 / 超时后受限回源
```

### 4.4 为什么不用布隆过滤器

商品 ID 为 UUID，可先过滤明显非法请求；对格式合法但不存在的 ID，空值缓存已能展示穿透保护。布隆过滤器还需处理初始化、增量同步和误判，因此本期选择更简单、可验证的空值缓存方案。

### 4.5 可观测性

全链路暴露 Prometheus 指标：

- 缓存：正常命中、空值命中、未命中、重建次数、锁竞争
- 数据库：回源次数、查询延迟、超时和错误
- 保护机制：限流次数、降级次数、信号量拒绝
- 链路定位：每个响应携带 `request_id`，结构化日志关联同一请求

## 五、数据模型与索引策略

### 5.1 商品主表 `products`

| 字段 | 设计 |
|------|------|
| `id` | UUIDv7，应用生成，兼顾多实例写入与 B-Tree 索引局部性 |
| 公共字段 | 标题、短标题、富文本详情、金额、库存、类型、状态、发货及退货规则 |
| `attributes` | JSONB，保存类型专属字段值 |
| `schema_version` | 商品绑定的字段模板版本 |
| `version` | 乐观锁版本号 |

金额使用 `NUMERIC(18, 2)`，API 以十进制定点值接收并以字符串返回，避免 JavaScript 二进制浮点精度问题。

### 5.2 索引策略

- 主键索引支持商品 ID 精确查询
- `(status, product_type, updated_at DESC, id DESC)` 支持管理列表组合筛选与稳定排序
- 标题关键词使用 PostgreSQL 全文检索 GIN 索引，避免前置通配符全表扫描
- JSONB 不建立无差别全属性 GIN 索引；只有被证实为高频筛选条件的属性才建立表达式索引

## 六、管理写链路与一致性

### 6.1 发布链路

1. 前端获取活动模板并动态渲染表单
2. 前端执行即时校验，提交类型、模板版本、公共字段和动态属性
3. 后端重新校验全部规则
4. 商品和图片元数据在同一 PostgreSQL 事务中写入
5. 事务成功后返回创建结果，公开详情缓存按首次请求惰性生成

### 6.2 编辑与状态更新

编辑请求携带 `version`，更新 SQL 同时匹配商品 ID 与预期版本，并原子递增版本。匹配不到时返回 `409`，阻止并发写入静默覆盖。

批量状态更新先在事务中锁定所有目标商品，再验证全部状态转换；任一商品不存在、版本冲突或状态非法时整批回滚。

### 6.3 缓存一致性

数据库事务提交成功后删除 Redis 详情快照。缓存删除失败不回滚已提交事务，而是记录指标并有限重试。方案接受一个由短 TTL 约束的短暂旧读窗口；本期不引入消息队列或 CDC。

## 七、API 设计

统一前缀 `/api/v1`：

| 方法与路径 | 用途 | 鉴权 |
|-----------|------|------|
| `POST /auth/login` | 管理员登录 | 否 |
| `GET /product-schemas/{type}/active` | 获取活动字段模板 | 是 |
| `POST /products` | 发布商品 | 是 |
| `GET /products` | 分页与组合筛选 | 是 |
| `GET /products/{id}` | 管理端完整详情 | 是 |
| `PUT /products/{id}` | 携带版本号编辑 | 是 |
| `PATCH /products/{id}/status` | 单个状态更新 | 是 |
| `POST /products/batch-status` | 批量上下架 | 是 |
| `GET /public/products/{id}` | 高 QPS 公开详情 | 否 |

错误响应统一包含 `code`、`message`、`field_errors` 和 `request_id`。主要状态码：`400`、`401`、`404`、`409`、`413`、`415`、`429`、`503`。

## 十一、关键设计取舍

| 决策 | 选择 | 原因 |
|------|------|------|
| 系统形态 | 模块化单体 | 控制 Demo 复杂度，同时保留清晰边界 |

| 详情读取 | Cache-Aside | 简单、成熟，缓存可从事实源重建 |

| 并发控制 | 乐观锁 | 商品编辑冲突低，避免长事务锁等待 |
| 缓存一致性 | 提交后删缓存 + TTL | 接受短暂旧读，避免本期引入 MQ/CDC |
| 扩容策略 | 指标驱动、逐步演进 | 避免未验证需求下的过度设计 |

## 十五、复盘与价值总结

### 15.1 做得好的地方

1. **领域模型先行**：状态机、金额精度、乐观锁、终态处罚等规则在代码层面显式表达，而非散落在 SQL 和控制器中
2. **防御性设计**：从空值缓存、热点锁、限流、降级到输入校验，每一层都有明确的故障隔离策略
3. **可验证性**：测试与压测不是事后的补充，而是与功能代码同步交付的验收标准
4. **诚实与克制**：README 和性能模板明确标注了「未验证项」「限制」「非生产承诺」，拒绝夸大

### 15.2 可改进的方向

1. **完整 PostgreSQL 集成重跑**：当前沙箱环境缺少 PostgreSQL / Redis / k6，部分集成与压测未能在最终环境复跑
2. **前端 UI 视觉层**：当前基于 Ant Design 默认主题，可进一步定制 Design Token 提升品牌一致性
3. **操作审计与日志**：题目未要求，但生产环境需要完整的操作审计链路
4. **缓存失效广播**：当前采用写后删缓存，多实例下允许短暂陈旧；大规模部署需引入消息队列或 CDC 广播失效

> **结语**
> 
> StockStack 的价值不仅在于「功能做完」，而在于展示了如何从**业务语义**出发，通过**版本化 Schema** 优雅地解决多态商品扩展问题，并通过**分层缓存防护体系**在高并发场景下保护系统稳定。每一个设计决策都附有取舍说明、测试验证和演进路径——这正是工程化思维的核心体现。
